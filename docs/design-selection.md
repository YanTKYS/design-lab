# デザイン選定ガイド

[README に戻る](../README.md)

ほかのリポジトリで画面を設計するとき、「どのデザインシステムを見比べるか」を決めるための資料です。各デザインの外観や画面構成は[デザイン比較ガイド](comparison-guide.md)に、画面を評価するときの観点は [UI 品質レビュー観点](ui-quality-review.md)にまとめています。

このガイドの候補は**比較を始めるための出発点**です。公式準拠やアクセシビリティ適合を保証するものではなく、デザインシステムの優劣や性能の順位でもありません。最終的な判断は、開発対象の業務要件・利用者の操作・アクセシビリティを優先して行ってください。

役割分担：開発全般の原則（構成・品質・運用など）は [lg_toolkit_guide](https://github.com/YanTKYS/lg_toolkit_guide) を正とし、このリポジトリはデザインごとの具体例と、選定・比較・レビューの参考に限ります。

## 1. 先に開発対象を確認する

候補を絞る前に、次の 6 点を短く書き出します。答えが決まらない項目は、比較のときに確かめる問いとして残します。

| 確認すること | 例 | 比較のときに見るところ |
| --- | --- | --- |
| 利用者 | 住民（初めて使う人）／職員（毎日使う人）／管理者 | 初めての人に説明が足りるか、慣れた人の操作が冗長にならないか |
| 主な作業 | 申請・届出の入力、台帳の検索と更新、集計の確認、文書の閲覧 | その作業に当たる画面（一覧・フォーム・ダッシュボード）の流れ |
| 画面の情報量 | 1画面の項目数、表の列数・行数、同時に見比べる数値 | 情報密度、行の追いやすさ、狭い幅での表の扱い |
| 操作頻度 | 年に数回／毎日数十件の処理 | 主要操作までの手数、キーボードだけで進められるか |
| 利用端末 | 庁内 PC（1280px 前後）／ノート PC／スマートフォン | 表示幅 1280・1024・768・375px での見え方 |
| 閉域・技術制約 | LGWAN などの閉域網、外部 CDN の可否、使えるフレームワーク、ブラウザの版 | 外部フォント・アイコン・スクリプトに頼った表現をしていないか |

閉域・技術制約は、見た目の好みより先に候補を左右します。たとえば外部 CDN や特定のフレームワークを使えない環境では、公式コンポーネントをそのまま導入できないデザインシステムがあります（このサイトの実装も、すべて CDN なしの独自実装です）。

## 2. 用途別の比較候補の例

よくある用途ごとに、最初に見比べる候補の例を挙げます。**ここに挙がっていないデザインを除外する意味はありません。** 2〜3 種に絞るときの手がかりとして使い、必要なら Plain を基準線として加えます。

| 用途 | 最初の候補 | 候補にする理由 | 比較で確かめること |
| --- | --- | --- | --- |
| 自治体の申請・届出（住民向け） | デジタル庁 / GOV.UK | 公共サービスの入力フォームと、必須表示・エラー・確認の流れを丁寧に設計している | 日本語の項目名と補足の読みやすさ、エラーから修正までの移動、確認画面での修正のしやすさ |
| 高密度のデータ管理（職員向けの台帳・一覧） | Carbon / Astryx | 表を中心にした業務画面のパターン（ツールバー・行の操作・絞り込みの状態表示）を持つ | 1画面に見える行数、絞り込み中であることの分かりやすさ、日本語の長いラベルで列やボタンが詰まらないか |
| デスクトップ的な編集ツール | Fluent 2 | コマンドバー・ドロワー・メッセージバーなど、Office 系アプリになじんだ操作の配置 | 主要操作がコマンドバーで見つかるか、詳細を開いたまま一覧を参照できるか |
| モバイル中心 | Material 3 | 狭い幅でのナビゲーション、検索、チップ、ダイアログの扱いが整理されている | 375px での表とフォームの操作、タッチしやすい大きさ、ナビゲーションの開閉 |
| 情報閲覧・ナレッジ | デジタル庁 / Plain | 本文の読みやすさと、見出し・表・文章だけで伝える構成を確認しやすい | 見出しの階層、長い文章の行長と行間、装飾がなくても要点が伝わるか |

候補を左右に並べるときは、[使い方の URL 仕様](usage.md#url-で共有と復元)で比較条件を URL にして記録すると、後から同じ状態を見直せます。例：`?mode=compare&left=dads&right=govuk&screen=form`、`?mode=compare&left=carbon&right=astryx&width=1280`。

## 3. 各デザインの向いている用途と注意事項

画面ごとの外観や部品の違いは[デザイン比較ガイド](comparison-guide.md#デザインごとの特徴)を参照してください。ここでは、比較を始める前に押さえておく点だけを挙げます。

| デザイン | 向いている用途の例 | 注目する UI パターン | 注意事項 |
| --- | --- | --- | --- |
| [デジタル庁デザインシステム](https://design.digital.go.jp/dads/) | 日本の行政サービス、住民向けの申請・届出、情報提供 | 必須・任意の明示、エラーの通知と欄ごとの理由、ステップ表示、日本語の本文の組み方 | 余白と文字が大きく、職員向けの高密度な一覧では表示できる行数が少なくなる。業務画面に使う部品が揃っているかは、公式サイトで最新の状況を確認する |
| [IBM Carbon](https://carbondesignsystem.com/) | 職員向けの高密度な業務ツール、データの一覧と一括操作 | ツールバー一体型のデータテーブル、行の展開、インライン通知、隙間なく並ぶボタンセット | 英語 UI を前提にした密度のため、日本語の長いラベルで列幅やボタン幅が足りなくなりやすい。住民向けの画面では情報量が多すぎることがある |

| [GOV.UK Design System](https://design-system.service.gov.uk/) | 初めて使う住民向けの手続き、1回だけ行う入力 | エラーサマリーからの移動、回答の確認と「変更」リンク、任意だけを明示するラベル | 英国政府のサービス向けで、本文 19px など英語に合わせた寸法。職員が毎日使う高密度な画面には合いにくい。本サイトは比較条件をそろえるため、1ページ1問の分割はしていない |

## 4. ほかのリポジトリで使う手順

1. **候補を 2〜3 種に絞る**：上の「先に開発対象を確認する」の 6 点を書き、用途別の例から候補を選びます。迷ったら Plain を基準線として加えます。
2. **同じタスクで見比べる**：開発対象の主な作業に近い流れを決め、すべての候補で同じ手順を試します。例：「申請番号で検索して詳細を開き、一覧へ戻る」「必須を空けて送信し、エラーから修正して確認まで進む」「同じ画面を 1280px と 375px で見る」。手順と確認の観点は [UI 品質レビュー観点](ui-quality-review.md#3-操作シナリオに基づくレビュー手順)を使います。
3. **採用／見送りの理由を短く記録する**：結論だけでなく、何を試して何が決め手になったかを残します。好みと、操作で確かめた事実を分けて書きます。

記録の例（開発対象のリポジトリの Issue や設計メモに貼る想定。内容は架空です）：

```md
## デザイン選定の記録

- 対象：○○課 台帳管理ツール（職員 10 名、毎日 30〜50 件を処理、庁内 PC 1280px）
- 制約：LGWAN 内で外部 CDN 不可、フレームワークは未定
- 比較した候補：Carbon / Astryx / Plain（基準線）
- 試したタスク：受付番号で検索→詳細→一覧へ戻る、状態で絞り込み→件数の確認、1280px と 1024px での表
- 採用する範囲：Astryx の絞り込み中の表示と表の下の内訳を参考にする／表・ボタンの部品は既存のものを使う／帳票の印刷画面は変えない
- 結果：
  - Astryx を参考にする：絞り込み中の警告と表の下の内訳で、表示中の件数を取り違えにくかった
  - Carbon は見送り：行の操作は分かりやすいが、日本語の列見出しが 1024px で折り返した
- 好みの意見（判断材料にしない）：Carbon の黒いヘッダーは引き締まって見える
- 残る論点：公式部品を使わない場合の実装範囲、スクリーンリーダーでの確認
- 比較 URL：https://yantkys.github.io/design-lab/?mode=compare&left=carbon&right=astryx&width=1024
```

## 選ぶときの注意

- **機械的に当てはめない**：「住民向けだから GOV.UK」のように用途の一致だけで決めず、開発対象の項目数・操作頻度・端末で試してから判断します。
- **一部だけを借りてよい**：採用は「デザインシステムを丸ごと導入する」ことに限りません。エラー表示や表の状態表示など、パターン単位で参考にするのも選択肢です。その場合は、借りた部分と自前の部分で操作の一貫性が崩れないかを確認します。
  - 部分採用では、**採用した部分／自前で設計する部分／影響させない部分**の境界を短く書き残すと、後から画面を変更する人（AI を含む）が迷いません。実例として、editor の [DESIGN.md](https://github.com/YanTKYS/editor/blob/main/DESIGN.md) は「Fluent 2 は外側の操作 UI に部分採用」「CodeMirror の編集領域・IME・入力は変えない」「色や寸法の値は既存の CSS を正本とする」を表と短い文で示しています。
  - 記録の置き場所は、各リポジトリの既存のドキュメント（README、開発者ガイド、設計メモなど）に合わせます。同じ名前のファイルを作る必要はありません。色コードやトークンの値は 1 か所を正本にし、記録には転記しないと、値のずれを防げます。
- **見た目の統一と画面の同一化は別**：組織内の複数のアプリで色や書体をそろえることと、用途の違うアプリ（申請フォームと台帳管理など）を同じ画面構成にすることは別の判断です。
- **このサイトの実装を公式の実物とみなさない**：各デザインの見た目・操作は公開資料を参考にした独自実装です。採用を決める前に、公式サイトの最新の資料と公式コンポーネント（使える場合）を確認してください。
