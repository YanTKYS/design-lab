# 案D「経路と停留所」設計資料

[探索の概要に戻る](README.md)

実装担当者向けの資料。名称は仮称。モックは [mock/d-list.html](mock/d-list.html)・[mock/d-form.html](mock/d-form.html)・[mock/d-dashboard.html](mock/d-dashboard.html)（[d.css](mock/d.css)）で、値は共通モデルから生成している。モックの HTML・CSS は見た目の参照で、実装の正本ではない。

## 1. 設計の核

**申請の処理を「路線」として描き、職員は停留所（状態）を選んで記録へ行き、住民は区間（入力のまとまり）をたどって申請を終える。**

旅客施設の案内表示について、国土交通省のガイドラインは、サインを誘導・位置・案内・規制の4種に分けて動線に沿って配置すること、誘導サインを動線の分岐点などに置くこと、路線などを色で表示する場合も文字を併記して色だけに頼らないこと、現在位置を赤で示す場合は下線や反転文字など形でも変化をつけることを挙げている。（[国土交通省「バリアフリー整備ガイドライン（旅客施設編）」2. 誘導案内設備に関するガイドライン（PDF）](https://www.mlit.go.jp/sogoseisaku/barrierfree/content/001913508.pdf)、掲載ページ：[公共交通機関の「バリアフリー整備ガイドライン」](https://www.mlit.go.jp/sogoseisaku/barrierfree/sosei_barrierfree_mn_000001.html)）

この4種を画面の部品に割り当てる。

| サインの種類 | 画面での役割 | 見た目 |
| --- | --- | --- |
| 案内（位置関係を示す） | 処理状態の路線図（一覧・集計）、入力の経路（フォーム） | 橙の太線と、形の異なる停留所の印 |
| 位置（いまどこか） | 選んでいる状態、現在の手順、ナビの現在の画面 | 黒地に白字の反転（「現在地」） |
| 誘導（次はどこへ） | 一覧への入口、「確認へ」、分岐点での次の操作 | 太字の下線＋「→」、黒の主ボタン |
| 規制（してはいけない・直す） | エラー | 赤の反転見出し＋「！」の印＋項目の太い赤線 |

**沖縄以外の主題にした理由**：申請管理の中心は「受付→審査→（補正依頼で戻る）→承認／却下」という手続きの順序で、職員が知りたいのは「どこで何件止まっているか」である。この順序と分岐を画面の骨格にすると、一覧の絞り込み・集計の内訳・フォームの進み具合を同じ図法で読める。この効用は地域の主題から導くより、移動のための案内表示の考え方（順序・分岐・現在地を図で示す）から導く方が直接的だと判断した。第一希望の沖縄案は案Cで満たしている。

## 2. 路線のかたち（3画面共通）

```text
                   ◇ 補正依頼   … 審査中から分かれ、審査中へ戻る支線（破線・⇅）
                   ┆
  ○ 受付済 ━━━━━━ ◉ 審査中 ━━┳━━━━ ◎ 承認済   … 本線の終点
                              ┗━━━━ □ 却下     … 分岐の終点
```

- 停留所の印は**形で区別**し、色を変えない：受付済＝白丸、審査中＝中心に点のある丸、補正依頼＝ひし形、承認済＝二重丸、却下＝四角。名称と件数を必ず併記する。
- 線（`#e0560f`）は装飾で、文字には使わない。線は `aria-hidden` の SVG、停留所は HTML のボタン／リンクにする（読み上げとキーボードの順は 受付済→審査中→補正依頼→承認済→却下）。
- 状態が増減した場合は、この図を描き直す必要がある（9. のリスク参照）。

## 3. 情報階層と読み順

1. 画面名と、ナビの現在地（反転）
2. 案内：路線図／経路。いま全体のどこにいて、何件あるか
3. 位置：選んでいる停留所（反転の「現在地」）と、表示中の件数（大きな数字）
4. 記録・入力そのもの
5. 誘導：次の操作（矢印付きのリンク、主ボタン）。分岐点＝結果の直後・フォームの最後に置く

## 4. 画面別の構成

### 申請一覧

- 上から：キーワード（入力欄＋「検索」）→ **処理状態の路線図**（灰色の案内パネル）→ 件数（「8件（71件中）」）と条件の札（「処理状態：審査中」）と「すべての状態に戻す」→ 台帳。
- 路線図の停留所が処理状態の絞り込み（既存の `status`）。押すとその状態だけを表示し、停留所が黒く塗られて「現在地」が付く（`aria-pressed`）。件数はキーワードに一致した数（既存の `statusOptions[].count`）。「すべての状態（71件）」はパネル右上のボタン。
- 台帳は共通の5列＋「詳細」ボタン。**処理状態の列は、経路上の位置を示す3点の小さな線（受付→審査→完了）＋状態名**。補正依頼は審査の位置、承認済・却下は完了の位置で、名前で区別する。
- 詳細は行の直下に全幅で開く。左に**この申請の経路**（受付日と受付方法 → 現在地：状態と担当課 → 処理期限）、右に残りの項目（申請者・ふりがな・申請種別・担当課・受付方法・備考）。経路の点はデータにある日付だけを使い、状態ごとの日付は作らない。
- 開いたら詳細の見出しへフォーカス、閉じたら「詳細」ボタンへ戻す。保持する状態は既存の `buildModel` の state（キーワード・状態・並べ替え・詳細・引き継いだ範囲）。

### 新規申請

- PC は2列：左（250px、`sticky`）に**入力の経路**、右（最大 720px）にフォーム。
- 経路：「1 入力」（現在地）の下に3つの区間（申請者情報・手続きの内容・確認事項）、その先に「2 確認」「3 完了」（破線の印＝この先）。区間ごとに状態を文字で出す：「✓ 入力済」／「！エラー n件」（エラーはひし形の赤い印）。区間名はそのまとまりへのリンク。区間の状態は `validate` の結果（送信後）から作り、送信前は「未入力」「入力中」などを出すかを実装時に決める（9. 参照）。
- フォーム：エラーのまとめ（赤の反転見出し「！ エラー　2件の入力を直してください」＋項目へのリンク）→ まとまりごとに見出し（停留所の印＋名称＋区間の状態、下に 3px の黒線）→ 項目。
- 項目：ラベル（17px 太字）＋札（必須＝黒地白字、任意＝白地黒枠）→ 補足 → エラー文（赤い丸の「！」＋文言）→ 入力欄（2px 黒枠、高さ 48px）。エラーの項目は左に 6px の赤線、入力欄の枠は 3px 赤。
- 最後に誘導：「次は『2　確認』です。…」の文と「確認へ →」（黒の主ボタン）。確認画面（モックなし）は経路の現在地を「2 確認」に進め、項目と値の表に各行「修正」、最後に「申請する →」。完了画面は経路の終点に現在地を置き、「申請一覧へ →」。

### ダッシュボード

- 集計条件：対象期間・担当課・「リセット」、右に基準日と期間の範囲。
- **4指標を路線図に組み込む**：
  - 左の「起点」の箱に受付件数（71件）と「受付した申請の一覧 →」。
  - 路線図の各停留所に件数と割合（受付全体に占める割合）。停留所は一覧へのリンク（`listStateFor` の `status`）。
  - 路線図の下に**区間の括り**：分岐の手前（受付済・審査中・補正依頼）を「処理待ち件数 19件」、分岐の先（承認済・却下）を「処理完了件数 52件」と「処理完了率 73.2%」で括る。処理待ち・処理完了は一覧へのリンク（`group`）、完了率はリンクなし。
- 月別の受付件数・申請種別ごとの受付件数は **1マス＝1件**の単位表（数えられる量なので）。マスの直後に件数の文字、種別は割合も併記。種別名は一覧へのリンク（`type`）。表は `table` で、マスは `aria-hidden`。

## 5. 幅による変形

| 幅 | 変形 |
| --- | --- |
| 960px 以上 | 一覧の詳細は経路（左 300px）と項目（右）の2列。フォームは経路とフォームの2列。集計は起点の箱を路線図の左、月別と種別を2列 |
| 600〜959px | フォームの経路はフォームの上に置く（固定しない）。詳細・集計は1列 |
| 600px 未満 | ナビは2×2（現在地は反転のまま）。路線図は同じ形のまま幅に合わせて縮め、終点の文字は縦に積む。案内パネルは画面の端まで広げる。台帳は1件ずつの塊（1行目に受付番号と「詳細」、2行目に経路の位置と状態名）。区間の括りは縦に積む。種別の単位表は名称を上、マスを下にする |

路線図は縦向きに回さない（どの幅でも左から右へ進む同じ図にして、覚え直しをなくす）。

- 書体：ゴシック1系統、見出し・ラベル・数値は太字。数値は `tabular-nums`。表示中の件数は 34px、集計の主要な数値は 44px。

- 罫：見出しの下・まとまりの下は 3px の墨。行は 1px の淡い灰。角は丸めない（すべて 0）。

## 7. 状態・操作の表し方

- **操作の優先順位**：主（墨の塗り＋白文字、「→」付き）＞副（白地＋2px 墨枠）＞文字（下線、行き先なら「→」）。1画面の主ボタンは原則1つで、分岐点（フォームの最後）に置く。
- **選択・現在地**：反転（墨の塗り＋白文字）。停留所は印を塗り、「現在地」の反転札を付ける。ナビの現在の画面も反転。
- **フォーカス**：墨 3px の輪＋外側に黄色 4px。反転（現在地）と重なっても見分けられる。
- **処理状態**：停留所の形＋名称（路線図）、3点の位置＋名称（台帳）。色は使わない。
- **エラー**：規制サイン。赤の反転見出し、「！」の丸印、項目の 6px 赤線と 3px 赤枠、エラー文。経路の区間にも「！エラー n件」を出し、区間名から該当のまとまりへ移れる。

## 8. ヘッダーを除いても残る個性

帯を外しても、(1) 処理状態が路線図・経路・3点の位置で「順序と分岐」として描かれる、(2) 現在地が常に反転の札で示される、(3) 集計が箱の並びではなく路線と区間の括りで読める、(4) 件数が1マス＝1件で数えられる、の4点で本文が識別できる。[本文だけの比較](README.md#本文だけで比べる)。

## 9. アセットとライセンス

- 画像・ピクトグラム・外部フォント・CDN は使わない。線は SVG の直線、印は CSS の基本図形。
- 実在の鉄道・バス事業者の路線色、駅ナンバリング、案内用図記号（JIS Z 8210）の図形は使っていない。ガイドラインは考え方の参照に限る。

## 10. 実装時に判断が残る箇所・リスク

| 箇所 | 内容 | 推奨 |
| --- | --- | --- |
| 状態の追加・変更 | 路線の形は5状態に合わせて描いている。状態が増えると図の描き直しが必要 | 停留所の位置（x・行）を状態の定義と一緒にデータで持ち、線はそこから描く |
| 路線図の高さ | 一覧の上で約 200〜240px を使い、台帳の開始が下がる | 職員の利用で行数が足りなければ、路線図を1行の縮小版（停留所と件数だけ）に切り替える選択肢を残す |
| 比喩の受け止め | 「路線」「現在地」が業務画面として軽く見える可能性 | 画面上の語は「処理状態」「現在地」「次は〜」に留め、乗車・駅などの語は使わない |
| 区間の状態（送信前） | 送信前に「入力済」をいつ出すか（入力のたびか、離れたときか） | 送信前は区間の状態を出さず、送信後（`submitted`）だけ出すと既存の検証の流れと矛盾しない |
| 黄色のフォーカス | 黄色の外輪は白地ではほぼ見えない（1.4:1）。墨の内輪が主 | 墨の輪を必須とし、黄色は補助とする |
| 停留所の操作 | 停留所のボタンが図の上に絶対配置され、狭い幅で当たり判定が近い | 当たり判定を 44px 以上にし、名称・件数を含む範囲全体を押せるようにする |
| 撮影環境の書体 | モックの画像は BIZ UD フォントのない環境（代替のゴシック体）で撮影 | Windows で終点の文字の折り返しを確認する |
