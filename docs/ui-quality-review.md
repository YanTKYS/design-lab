# UI 品質レビュー観点

[README に戻る](../README.md)

画面のレビューで確認する観点と、実際に操作して確かめる手順をまとめた資料です。人が作った画面にも AI が生成した画面にも使えます。どのデザインを見比べるかは[デザイン選定ガイド](design-selection.md)、このサイトの各デザインの特徴は[デザイン比較ガイド](comparison-guide.md)を参照してください。

点数の合計や一律の合格基準は設けません。レビューの目的は、**利用者の作業を妨げている点を、根拠とともに見つけて直すかどうかを決めること**です。

## 1. レビューの前提

- **好みと業務効率を分ける**：「すっきりして見える」「古く見える」は好みの意見です。「検索から詳細まで 3 回の操作で届いた」「エラーの理由を読んでも直し方が分からなかった」のように、操作して確かめた事実と分けて記録します。
- **根拠のない断言をしない**：計測や利用者での確認をしていない場合、「操作が速い」「アクセシビリティ基準に適合している」とは書きません。「キーボードだけで最後まで進めた」「コントラスト比を測って 4.5:1 以上だった」のように、確かめた範囲を書きます。
- **見た目の統一と画面の同一化を混同しない**：同じ組織のアプリで色・書体・用語をそろえることは有益ですが、用途の違う画面を同じ構成にそろえることとは別です。たとえば住民向けの申請フォームと職員向けの台帳一覧では、適切な情報密度が異なります。
- **このサイトの実装は参考例**：各デザインの画面は公開資料を参考にした独自実装で、公式準拠を示すものではありません。レビュー対象との比較には使えますが、正解の見本ではありません。

## 2. 観点

各観点の問いに、対象画面を操作しながら答えます。右の列は、このサイトで同じ観点を見比べられる場所です。

| 観点 | 確認の問い | このサイトで見比べる場所 |
| --- | --- | --- |
| 情報階層 | 画面を開いて最初に目に入るのは、利用者が最初に知るべきことか。見出し・本文・補足の強弱が内容の重要度と合っているか | ダッシュボードの指標と内訳の並び、一覧の見出しと件数表示 |
| 主要操作の発見性 | その画面で最も多い操作（検索、新規作成、保存など）がすぐ見つかるか。主操作と副操作の見た目が区別されているか | 一覧の「新規申請」と行の「詳細」、フォームの「確認へ」と「キャンセル」 |
| 情報密度 | 作業に必要な情報が 1 画面に収まるか。逆に、詰め込みすぎて行を追えなくなっていないか。利用頻度に合っているか | 一覧の行の高さと 1 画面の行数（Carbon・Astryx と GOV.UK・デジタル庁を並べる） |
| 一貫性 | 同じ意味の操作や状態が、画面をまたいで同じ名前・見た目・位置か。ボタンの文言と結果の表示が対応しているか | 処理状態の表し方（一覧・詳細・ダッシュボード） |
| フィードバック・エラー表示 | 操作の結果（絞り込み中、保存した、失敗した）が分かるか。エラーは何が起きたかと直し方を示し、該当の欄へ移動できるか | フォームの「エラーを再現」、一覧の絞り込み中の表示と空の結果 |
| キーボード・フォーカス | Tab だけで主要な作業を最後まで進められるか。フォーカスの位置が常に見えるか。ダイアログを閉じると元の位置へ戻るか | 一覧の詳細を開いて Esc で閉じる、フォームのエラー後のフォーカス |
| 狭い画面 | 狭い幅で、内容や操作が消えたり重なったりしていないか。表は横スクロールなどで全列を確認できるか | 表示幅 375px・768px |
| 日本語・IME | 変換中に入力が確定・消失しないか。長い日本語のラベルで折り返しや省略が起きても意味が通るか。全角・半角の扱いを示しているか | 一覧のキーワード、フォームの氏名・ふりがな（左右比較で同期を確認） |
| 不要な装飾 | 影・グラデーション・アイコン・区切りなどの装飾が、情報の区別や操作の手がかりになっているか（次の節を参照） | Plain と各デザインを並べ、装飾を外しても伝わるかを見る |

### AI が生成した画面で目立ちやすい装飾（AI slop）

AI が生成した画面には、内容や用途と関係なく同じ表現が繰り返し現れる傾向があります（いわゆる AI slop）。次の表現は**禁止ではありません**。どれも目的があれば正当に使えます。レビューでは「この画面で、この表現は何を伝えているか」を確認し、答えられないものを削る候補にします。

| 表現の例 | 確認する問い | 目的があると言える例 |
| --- | --- | --- |
| 意味のないグラデーション・色のにじみ | 色の変化が、値の大小や状態など何かを表しているか | 連続する値を色の濃淡で示す地図や凡例 |
| すべての要素に付いた同じ影 | 影が重なり順（手前に浮いている）を示しているか | 下の画面の上に開くダイアログやメニュー |
| 内容を同じ大きさのカードに切り分ける | 切り分けた単位が、独立して扱う情報のまとまりか。カードにしたことで比較しにくくなっていないか | 個別に開く・並べ替えるレコードの一覧 |
| 装飾的な英語ラベル（「OVERVIEW」「INSIGHTS」などの大文字の小見出し） | 利用者の言葉で、内容を説明しているか。見出しの上に重ねる必要があるか | 製品内で確立した用語・画面名として使われている場合 |
| 根拠のない番号付け（01 / 02 / 03） | 内容が本当に順序のある手順か | 入力→確認→完了のように順に進む手順 |
| 過剰な余白 | 余白が、まとまりの区切りや読みやすさのためか。作業に必要な情報が画面の外へ押し出されていないか | 初めて使う人向けの、1画面 1 つの問いの入力 |
| 見出しや項目ごとのアイコン | アイコンが、文字だけでは区別しにくい種類や状態を補っているか | 状態（承認済・却下など）を色だけに頼らず示す |
| 1 語だけ色や太字を変えた見出し、大きな数値＋小さな説明＋装飾のヒーロー | 強調した部分が、利用者が最初に知るべきことか | 指標画面で、判断に直結する数値を目立たせる |
| すべてのカードのホバー動作や、各セクションが下から現れる動き | 動きが、操作の結果や変化を知らせているか | 開いた・閉じた・追加されたことを示す動き |
| ボタンやリンクの末尾の「→」、中黒でつないだ説明（A・B・C） | 記号が、移動先や区切りを利用者に正しく伝えているか | 別のページへ移動することを示すリンク |

参考：[Anthropic frontend-design Skill](https://github.com/anthropics/skills/tree/main/skills/frontend-design) は、AI の画一的な表現を避ける考え方として、カードの一律の角丸と影、装飾的なグラデーション、大文字の小見出し、内容が順序でない番号付けなどを「既定値であって選択ではない」例に挙げています。このガイドはその考え方を参考にしていますが、Skill を導入するものではありません。業務画面では、独自性よりも、用途に合った情報密度と操作の分かりやすさを優先してください。

## 3. 操作シナリオに基づくレビュー手順

画面を眺めるだけでなく、利用者の作業に近い操作を実際に行い、その結果を記録します。開発対象の主な作業に合わせてシナリオを選び、必要なら書き換えてください。

### シナリオ A：検索→詳細→戻る

1. 一覧で、受付番号や名前の一部で検索する。
2. 処理状態などで絞り込み、表示件数を確認する。
3. 1 件の詳細を開き、必要な情報を読む。
4. 詳細を閉じて一覧へ戻る。

確認すること：検索条件と件数が常に見えているか／絞り込み中であることが分かるか／詳細に必要な項目がそろっているか／閉じた後に元の行と検索条件が保たれているか（フォーカスも戻るか）／キーボードだけで同じ流れを進められるか。

### シナリオ B：フォームの入力エラー→修正→確認

1. 必須の項目を空け、形式の誤った値を入れて送信する。
2. エラーの件数と各項目の理由を読み、最初のエラーへ移動する。
3. 1 項目ずつ直し、エラーの表示が消えることを確認する。
4. 確認画面で内容を見直し、編集へ戻ってから再び確認へ進む。

確認すること：エラーの理由が直し方を示しているか／エラーの欄へ移動できるか／直した後に表示が更新されるか／戻っても入力が消えないか／日本語の変換中に入力が崩れないか／必須・任意の区別が先に分かるか。

### シナリオ C：同じ内容をデスクトップと狭い幅で見る

1. 同じ画面を 1280px 前後と 375px で開く。
2. シナリオ A または B の一部を狭い幅でも行う。

確認すること：狭い幅で操作や情報が消えていないか（隠すならどこから開けるか）／表の全列を確認できるか／ボタンが押しやすい大きさか／ナビゲーションの開閉が分かるか。

このサイトでは、左右比較と表示幅の切替で、同じシナリオを複数のデザインで続けて試せます（[使い方](usage.md)）。

## 4. レビュー依頼の例

### 人に依頼する場合

```md
次の画面をレビューしてください。対象は○○課の職員が毎日使う台帳の一覧画面です（庁内 PC、1280px）。

- 試してほしい操作：受付番号で検索→詳細を開く→一覧へ戻る。1024px と 375px でも同じ操作。
- 見てほしい観点：絞り込み中であることが分かるか、主要操作が見つかるか、キーボードで最後まで進めるか。
- 書き方：気になった点ごとに「どこで・何をしたら・どうなったか」と、直す必要があると思うかを書いてください。見た目の好みは分けて書いてください。
```

### AI に依頼する場合

```md
次の画面（スクリーンショット／HTML）を、UI 品質の観点でレビューしてください。

- 画面の目的：職員が台帳を検索し、1 件ずつ状態を更新する。利用頻度は毎日数十件。
- 想定する操作：検索→詳細→一覧へ戻る、必須を空けて保存→エラーから修正。
- 観点：情報階層、主要操作の発見性、情報密度、一貫性、フィードバック・エラー表示、キーボード・フォーカス、狭い画面、日本語・IME、不要な装飾。
- 装飾（影、グラデーション、カード分割、英語の小見出し、番号付け、アイコンなど）は禁止ではありません。それぞれ何を伝えているかを確認し、目的が見当たらないものだけを指摘してください。
- 指摘ごとに「対象・指摘・根拠・対応要否の提案」を書いてください。画面から確認できないこと（操作速度、支援技術での動作、基準への適合）は推測で断言せず、「未確認」と書いてください。
- 点数や合否は付けないでください。
```

## 5. 判断記録の最小フォーマット

指摘ごとに次の項目を残します。対応しないと決めた指摘も、理由とともに残します。

| 項目 | 書くこと |
| --- | --- |
| 対象画面 | 画面名と状態（例：申請一覧、状態で絞り込み中、375px） |
| 目的 | その画面で利用者が行う作業 |
| 指摘 | どこで・何をしたら・どうなったか |
| 根拠 | 操作して確かめた結果、測定値、参照した資料。好みの意見はその旨を書く |
| 対応要否 | 直す／直さない／保留と、その理由 |

記入例（内容は架空です）：

```md
| 対象画面 | 目的 | 指摘 | 根拠 | 対応要否 |
| --- | --- | --- | --- | --- |
| 申請一覧（状態で絞り込み中、1280px） | 処理待ちの申請を探す | 絞り込み中であることが件数の表示からしか分からない | 状態を「審査中」にしたまま別の操作へ移り、戻ったときに全件と誤認した（1 名で確認） | 直す：絞り込み中の表示と「条件をクリア」を表の上に置く |
| ダッシュボード（1280px） | 月の処理状況を把握する | 指標カードの背景のグラデーションが何も表していない | 値や状態と色の対応がない | 直す：単色の面にする |
| 入力フォーム（375px） | 住民が申請する | 見出しの上の英語の小見出しが不要と感じる | 好みの意見（操作への影響は未確認） | 保留：用語を利用者に確認してから決める |
```
